## Why schema v2 was required

The Gate O implementation stored only the latest observed sitemap `lastmod`. If more changed detail URLs existed than `delta_detail_limit`, updating the full sitemap snapshot before processing the bounded batch could acknowledge unprocessed changes and make them disappear on the next run.

Gate S separates:

```text
lastmod          = latest issuer-observed version
fetched_lastmod  = latest successfully processed version
pending_since_at = durable unprocessed-work marker
```

A sitemap snapshot can therefore advance observation state without falsely advancing processing state.

Baseline behavior is also explicit:

- historical pages outside the initial lookback are acknowledged without a historical crawl-all;
- baseline candidates that temporarily fail remain pending;
- those baseline-debt rows retain one-time signal suppression until first successful processing, preventing a later false `NEW` signal.

## Availability / recovery policy

S13 Source Registry now freezes these R5 operating objectives:

```text
poll interval                  = 900s
recovery retry interval        = 300s
delta detail limit             = 20
availability class             = DELAY_TOLERANT_MONITORED
business-data RPO target       = 900s
collection RTO / recovery SLO  = 1800s
accepted collection outage     = 3600s
```

These are internal operating objectives for this slice, not an external customer SLA.

When a missed window is detected, scheduler rows are marked:

```text
trigger_kind=RECONCILIATION
recovery=1
outage_window_start=<durable start>
outage_window_end=<durable end>
```

The recovery window remains open while backlog exists. Each run processes at most the source `delta_detail_limit`; if backlog remains, the source becomes due again on the bounded retry cadence rather than triggering an immediate crawl-all.
